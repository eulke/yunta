  Install packs in the user's Yunta state directory for use across projects

  you asked    add pack global instalation support, not only project level as
               today

  Add user-wide pack installation alongside project-local vendoring. A global
  pack lives under the existing YUNTA_HOME (or ~/.yunta) state root, so every
  project using that same user state can discover it. `yunta pack add --global`
  installs there; local installs continue to use the repository tree. Resolution
  prefers a project-local pack when the same workflow is available locally, then
  falls back to global packs. Pack locks and list/remove operations remain
  scoped to the selected installation level.

  decided for you

    1  What scope and persistence does a global installation have?
      chose        Store global packs under `$YUNTA_HOME/packs` (or
                   `~/.yunta/packs`) and make them available to projects run by
                   that user state root.
      instead of   A system-wide shared directory
                   A configurable directory per installation
      because      Yunta already defines and shares a user state root through
                   YUNTA_HOME; using it keeps global availability aligned with
                   existing user state and test isolation.

    2  How does a user select global rather than project installation?
      chose        Add `--global` to `yunta pack add`; add `--global` selectors
                   to pack list, remove, update and audit so lifecycle actions
                   address the intended store.
      instead of   A separate `pack install --global` command
                   Global installs as the default
      because      The explicit flag preserves the established project-local
                   default and makes the target visible on every mutating or
                   inspection command.

    3  What happens when local and global installations expose the same workflow
       or pack?
      chose        Project-local catalog entries take precedence over global
                   entries; global entries are fallback candidates. Ambiguity
                   within either level remains an error. Permit same pack
                   identity in both stores and keep independent lock entries.
      instead of   Global overrides local
                   Refuse duplicate pack identities across levels
      because      Local project state is the most specific choice, while
                   independent stores allow a project to pin a different version
                   without changing the user's installation.

    4  Which lifecycle, permission, and compatibility behaviors are in scope?
      chose        Support global add, update, remove, list and audit with
                   separate global locks; preserve existing audit, schema and
                   executor checks for either target. Do not migrate existing
                   project installs.
      instead of   Only add global installs
                   Automatically migrate project installs
      because      A useful persistent user-level install needs the existing
                   management operations and safety gates; migration is
                   unnecessary and could unexpectedly change checked-in project
                   state.

  risks
    ^ Global lock state is user-specific and is not committed with a project, so
      different users may have different fallback pack versions.
    ^ Global catalog lookup must be threaded through every workflow, skill,
      agent, frozen-layer and prompt discovery path that currently reads only
      project packs.

  left out
    . Migrating existing project installations to global storage.
    . Sharing global installs between operating system users.

  design
    `PackInstallScope` selects the root before the existing staging, vendor,
    lock and management operations run. Project scope uses `<repo>/.yunta`;
    global scope uses the Yunta user state root. Runtime catalog readers receive
    the global packs root from the process environment and inspect local packs
    first, then global packs, retaining the existing ambiguity rule within a
    source. Locks remain separate: project installs use `.yunta/yunta.lock`;
    global installs use `$YUNTA_HOME/yunta.lock`.
