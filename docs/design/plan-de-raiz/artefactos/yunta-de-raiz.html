Los doce vicios y sus mecanismos

Un vicio es una forma de escribir código que produce el mismo defecto en cualquier módulo donde se aplique. Un mecanismo es la forma que hace que ese defecto no se pueda escribir. Cada tarjeta nombra el vicio, la evidencia más fuerte, el mecanismo, y el patrón del repo que ya lo encarna.

                EventPayload::Findings(e)  => state.findings.apply(e, event),
                EventPayload::Artifacts(e) => state.artifacts.apply(e, event),
                EventPayload::Gates(e)     => state.gates.apply(e, event),

Siete flujos punta a punta

Cómo funciona cada cosa en la arquitectura objetivo, paso a paso, con la función que da cada paso.

F1 · Agregar un kind de evento

  1. En core/events/<dominio>/kinds.rs se agrega la variante con su nombre y versión. Es el único lugar.
  2. payloads.rs del dominio gana el struct y su constructor. Sin constructor público, nadie lo puede construir.
  3. ledger.rs::apply no compila hasta que el kind tenga brazo — o se declare Audit por nombre.
  4. happening.rs no compila hasta que el kind tenga lectura.
  5. KINDS, kind_name, all_kinds(), events.json y los "36" se derivan; xtask schema regenera; el test de docs exige la fila del Contrato y la sección del spec.

Antes: 9 sitios + 2 docs, 3 defendidos. Después: 3 sitios en un módulo, todos defendidos, el resto derivado.

F2 · Un nodo corre

  1. exec lee el log una vez y derive produce RunState (todos los ledgers, un pase).
  2. decide(&workflow, &state, &policy) devuelve Decision::Execute(node, attempt) — el attempt lo dice NodeLedger.
  3. execute construye NodeStarted::attempt(n) y lo registra por RunLog::record; el observer lo espeja al pintor.
  4. Según el kind, la cáscara corre bash por spawn_governed, o arma un SessionPlan (F3), o publica un gate (Escalation::new) y devuelve GateStep::Waiting(PauseReason).
  5. close_node verifica artifacts (Answerer::{Log,Staging}), y registra NodeFinished::new(outcome, tokens) o NodeFailed::new(Failure, …) — un constructor cada uno, un escritor cada uno.
  6. progress.md se escribe por tokio::fs desde RunState, no por otro replay.
  7. Cada evento llega al pintor: Folded → run_frame (región) y chronicle (scrollback y líneas), mismas palabras.

F3 · Una sesión se abre

  1. resolve_node_runner elige chosen: RunnerCandidate y registra runner_resolved.
  2. SessionPlan { node, task, prompt, chosen, profile, artifact_dir, resume }.
  3. open_session(plan, adapter) llama require(cap) por cada campo gobernado; cada ausencia produce una Degradation::new(cap, adapter, Policy) desde la tabla — o falla el nodo, según la fila.
  4. SessionRequest sale con modelo y agente de chosen, edit_constraints solo si EditHooks, skills solo si Skills, endpoint solo si RunTools.
  5. dispatch_session (sin cambios): resume o spawn, pgid registrado, stream plegado a eventos de auditoría con Result, ToolTarget digest.
  6. Cancel/budget: interrupt → gracia → kill al grupo; un kill fallido es un engine_finding.

F4 · Un artifact vive

  1. produces: [tasks, "report-{{inputs.name}}.md"] parsea a ArtifactSpec::{Interpreted(Tasks), Opaque(ArtifactName)}; el nombre se valida como escrito y otra vez después de renderizar.
  2. Interpretado: la sesión entrega por yunta_submit_tasks {document} (RunTool enum), shape::accept valida, canonical renderiza, accept(…, RecordedOrigin::Submitted) guarda por hash y proyecta la vista. Opaco: la sesión escribe en su staging.
  3. Al cierre, Answerer dice quién responde por cada declaración; held_document o verify_one; el veredicto en sesión (yunta_check_artifact) llama a la misma función.
  4. ArtifactLedger (sin cambios) es la única respuesta a "qué tiene el run"; nadie lee artifacts/.
  5. Answers es ArtifactKind::Answers: el engine lo escribe y lo lee por la misma puerta que los demás.

F5 · Cualquier comando abre un run

  1. Context::load() lee Env una vez y resuelve el proyecto.
  2. ctx.open_run(&run_id)? → Opened o CliError::RunNotFound { id, roots } — una oración, un lugar.
  3. opened.manifest es PersistedDoc<Manifest>: versión leída, desconocidos marcados.
  4. El comando deriva (run_frame/derive/chronicle) y renderiza con RunWord/NodeDisplay/advice.
  5. Sale por Outcome ← RunWord y main mapea una vez a exit code.

  2. La ausencia es un capability_degraded con Policy tipada, registrado por RunLog.
  3. DegradationLedger la sostiene; RunFrame.degraded, el receipt, stats y verify la muestran (hoy solo el frame).
  4. La crónica la dice: ! implement — edit hooks not declared by codex: scope checked after the session.

P1 · el puerto

¿El puerto de adapters vive en yunta-core::port o en un crate propio yunta-port? P8 · los bugs de comportamiento, ahora o por fase

Trece de los defectos no son de forma: cambian lo que un run hace hoy. Cada uno lo cierra un mecanismo de las fases 2–6. La pregunta es si cinco de ellos —los que exponen un secreto, escapan del run dir, corren en el modelo equivocado, muestran findings retirados o dejan un git colgado— se corrigen antes, como PRs propios. Recomiendo sí, con una regla: cada corrección es el mecanismo aplicado a ese único sitio, no una tercera copia. La sección siguiente los lista con su fix y si cumple esa regla.

El plan por fases

Ocho fases, cada una un PR o una serie corta, ordenadas por lo que desbloquean. Ninguna fase deja una pieza "para después": cada una termina con su gate completo en verde, sus textos en presente y su ADR registrado.

fase 0 · decisiones y corpus

P1–P7 registradas; corpus des-corrompido; docs_sync recursivo

Un ADR por decisión (por archivo, estrenando el formato). El pase mecánico sobre Contrato y RFCs. docs_sync.rs recorre docs/design/ y parsea todo YAML — la config de referencia se corrige en el mismo PR. Los ratchets nuevos sembrados con el conteo de hoy. Desbloquea: que la documentación pueda perder, y por lo tanto ganar.

fase 1 · el puerto

M01: core::port, core::process, testkit partido, mock renderer en su crate

Movimiento de tipos sin cambio de comportamiento; test de frontera no_adapter_crate_in_engine. core y adapters enlazan testkit-core; los helpers duplicados de adapters se unifican. Desbloquea: la tabla capacidad→política en core (fase 3) y el arnés único (fase 6).

fase 2 · eventos por dominio
