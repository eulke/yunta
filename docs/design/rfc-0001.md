# RFC-0001 — Yunta: visión y arquitectura

**Estado:** aceptado · **Alcance:** visión, posicionamiento, arquitectura de capas y modos de ejecución.

## 1. Problema
Cuando se le pide a un agente de IA "arreglá este bug", lo que ocurre depende del humor del modelo: puede saltear la planificación, olvidar los tests, marcar completado trabajo no hecho, o desviarse del plan sin que nadie lo detecte hasta que es caro. La causa raíz: las reglas viven en prosa interpretada por LLMs, la verificación la hace el mismo que ejecuta, y el estado vive en ventanas de contexto que se degradan y mueren.

## 2. Solución
Yunta codifica el proceso de desarrollo como **workflows YAML** que un **engine determinista en Rust** ejecuta. El engine es dueño del estado (event sourcing), de la verificación (criterios ejecutables, scope, baseline) y de la orquestación (DAG, loops, gates, re-rutas, composición). Los agentes solo aportan inteligencia dentro de nodos acotados, con contexto inyectado y presupuesto controlado.
Posicionamiento: lo que Dockerfiles fueron para infraestructura y GitHub Actions para CI/CD, Yunta lo es para flujos de AI coding — con verificación mecánica del trabajo como diferencial central.

## 3. Requisitos de origen
- Usable desde Claude Code, Codex y otros agentes; base para armar flujos.
- Escalar a las pretensiones de cualquier equipo.
- Skills enchufables.
- Resumibilidad total, tareas de horizonte largo (días/semanas), inyección de fuentes de contexto.
- Procesos multi-persona y multi-etapa (workflows compuestos).

## 4. Principio: Yunta es un engine, no un proceso
Yunta no propone ni encarna ningún flujo de trabajo. El engine no sabe qué es planificar, revisar o shipear: sabe ejecutar nodos, verificar criterios, llevar estado y coordinar personas. Los procesos los define cada equipo en sus workflows — eso es lo que hace que escale a las pretensiones de cualquiera.
Dos precisiones que evitan malentendidos:
- **Impone una forma, no un flujo.** Los nodos `invariant: true`, los criterios ejecutables, el scope declarado y el pre-check en rojo no son opinión sobre el proceso ajeno: son la definición operativa de "trabajo verificado". Cualquiera arma el flujo que quiera; lo que nadie puede armar es uno donde el agente se autocertifique. Esa es la única opinión de Yunta, y es su razón de existir.
- **Los workflows de fábrica son contenido, no producto.** No vienen embebidos en el binario: se distribuyen como **packs instalables** (RFC-0002), sin más estatus que los de un tercero, y se pueden ignorar o borrar sin tocar el engine:
	- `yunta/starter` — pack mínimo: dos o tres workflows cortos que enseñan la forma (un `fix` de un solo nodo verificado, un `review` con fan-out) y sirven de punto de partida y de fixture.
	- `yunta/fragua` — pack de referencia completo: el flujo de ingeniería extremo a extremo (grill → plan con ledger → implementación verificada → validación → review multi-runner → PR con recibo), modos abiertos y destilado a knowledge. Es la demostración de lo que el engine permite, no lo que el engine es.
Consecuencia para la documentación: el README enseña **primero a escribir un workflow de tres nodos desde cero**, y recién después menciona los packs. Quien lea la doc debe terminar sabiendo construir el suyo, no sólo correr los ajenos.

## 5. Arquitectura de capas
1. **Core / engine**: ejecutor de DAG sobre tokio; tipos de nodo `prompt`, `bash`, `loop`, `gate`, `check`, `parallel`, `executor`, `workflow`. Grafo con petgraph; scheduler dispara nodos al completarse sus deps. Event sourcing a SQLite en modo WAL — único backend (D53) — en el crate `yunta-storage`, detrás de una interfaz mínima que hace de cualquier motor futuro un adapter nuevo, no una migración.
2. **Adapters**: crate `yunta-adapters` — traits `Adapter` y `AgentSession` (ver Spec). Lanzan CLIs en modo headless con salida JSON en streaming, traducida a eventos tipados. Builtin: `claude-code`, `codex`, `mock` (primera clase, para CI sin LLM).
3. **Aislamiento**: por default un worktree de git por run (shell a `git`, más robusto que git2 para worktrees), en árbol separado del run.dir — runs paralelos sin conflictos; `isolation: none` para trabajar sobre el checkout actual bajo las condiciones del Contrato §7.3.
4. **Skills**: directorios con [SKILL.md](http://SKILL.md) + assets montados por nodo; resolución en capas repo \> usuario \> org. Nodos determinísticos extensibles vía executors externos con contrato JSON por stdin/stdout (D47), sin recompilar el engine.
5. **Exposición**: CLI (clap) para humanos y CI; servidor MCP (crate oficial rmcp) para que los agentes invoquen workflows como tools; y una skill instalable en el repo destino que le enseña al agente cuándo usar Yunta.

## 6. Un binario, dos modos
| Modo | Quién lo lanza | Vida |
|---|---|---|
| `yunta run ...` | humano o CI | dura lo que el workflow |
| `yunta mcp` | **el cliente MCP** (Claude Code lo lanza como subproceso por stdio) | vida de la sesión del cliente; sin puerto, sin daemon |
"Servidor MCP" es un rol del protocolo, no un servicio desplegado: en transporte stdio el cliente lanza y mata el proceso. **Ningún modo de Yunta requiere infraestructura** — no hay daemon alguno. Las capacidades de equipo (estado compartido, gates remotos, dashboard, notificaciones de equipo) pertenecen a un proyecto separado con su propio repositorio y ciclo de vida (D77); el engine no lo menciona ni depende de él.

## 7. Clasificación organizacional
Yunta es **librería/tooling sin infraestructura**: se compila, se distribuye como binario, corre en la máquina del dev o en un runner de CI, y termina. Sin servidores, instancias ni deploys — sin excepciones (D77). `yunta mcp` no es un daemon: el cliente MCP lanza el proceso por stdio y lo mata al cerrar.

## 8. Estructura del código
**Workspace de Cargo.** Los crates hacen que las fronteras del diseño las imponga el compilador en lugar de la disciplina: `yunta-engine` no puede importar SQLite ni conocer un CLI concreto porque esos crates no están en sus dependencias — A1 y D53 dejan de depender del checklist de PR. Beneficio adicional: compilación incremental por crate y la opción de publicar el engine por separado si alguien quiere embeberlo.
```javascript
yunta/
├── Cargo.toml            # workspace
└── crates/
    ├── core/             # package yunta-core — tipos, IDs, errores, eventos, schema
    ├── storage/          # package yunta-storage — SQLite; depende de core
    ├── adapters/         # package yunta-adapters — trait Adapter + claude-code, codex, mock
    ├── engine/           # package yunta-engine — scheduler, ciclo de tareas, contexto, verificación
    └── cli/              # package yunta — el binario (clap, comandos, render)
```
Packages prefijados ([crates.io](http://crates.io) es un namespace plano y global: `core` o `engine` no son publicables), directorios sin prefijo (convención del ecosistema), y el binario se llama `yunta` a secas — es el comando y lo que se instala. El grafo de dependencias es acíclico y unidireccional: core ← storage/adapters ← engine ← cli. La distribución no cambia: sigue siendo **un único binario estático**. Sin features de Cargo: no hay `serve` (proyecto separado, D77) ni `postgres` (D53) — un solo build, una sola matriz de CI. Los tests de integración viven en cada crate y ejercitan el engine con el adapter `mock`.

## 9. Estado del repo destino
```javascript
.yunta/
├── config.yaml        # versionado — config del repo (capa más específica)
├── workflows/         # versionado — workflows del equipo
├── skills/            # versionado — skills del equipo
├── knowledge/         # versionado — conocimiento durable (ADRs, CONTEXT.md)
├── packs/             # versionado — packs vendoreados (RFC-0002)
└── yunta.lock         # versionado — packs pineados por hash
~/.yunta/              # usuario: config, runs/, worktrees/, DB (ubicación configurable, Contrato §2.2)
```
Capas de config (mayor precedencia primero): repo → usuario → org — con la única excepción de `permissions`, cuya precedencia se invierte (Contrato §6.1). Merge por clave; arrays se reemplazan.

## 10. No-objetivos
- Triggers asincrónicos entre workflows sin padre común (territorio del CI del equipo, o del proyecto de servidor separado).
- Condicionales complejos estilo BPMN (re-rutas + gates cubren corrección y decisión humana).
- Mensajería directa agente-a-agente (ver Contrato: comunicación mediada por el engine).
- Emular capacidades ausentes de un adapter (degradación explícita siempre).
