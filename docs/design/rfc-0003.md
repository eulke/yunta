# RFC-0003 — Diferenciales de producto

**Estado:** aceptado · **Alcance:** los diferenciales de producto que convierten la arquitectura en valor visible. Criterio de selección: valor agregado dividido por distancia respecto de lo construido — las cuatro apuestas caen casi gratis del event sourcing y son inimitables sin reconstruirlo.

## 1. Recibo de trabajo verificado (feature insignia)
Al cierre de un run, el engine emite un **certificado adjuntable al PR**, derivado íntegramente del event log — evidencia mecánica encadenada, jamás un resumen redactado por LLM:
```javascript
Verified Work Receipt — run 01J8...
✓ 23/23 criteria green (commands + exit codes listed)
✓ 0 regressions vs baseline (suite hash a3f2...)
✓ Scope clean: full diff within declared globs
✓ Reviewed by 2 independent runners (claude-code, codex)
• Cost: N tokens · CPTV: N tokens/task (est. $X if `pricing:` configured) · 2 reroutes
• Event chain: 342 events, hash-linked, replayable
```
Por qué es la insignia: la pregunta del mercado es "¿cómo confío en código generado por IA?" y las respuestas existentes son declarativas ("usamos buenos modelos"). El recibo es un artefacto auditable que un gerente, auditor o cliente puede ver sin entender DAGs — convierte el diferencial técnico profundo (verificación del engine, I5/I7) en un objeto tangible. Conexión con **A-06** (firma criptográfica): recibo firmado = atestación, cuando se implemente. Formatos: markdown para PR, JSON para máquinas. Costo: un formateador sobre datos existentes.

## 2. Time-travel debugging: `yunta replay` / `yunta diff`
Como cada nodo registró exactamente qué contexto vio (hashes por segmento, D42) y todo evento está secuenciado, el engine puede reconstruir **lo que cualquier agente tenía delante en cualquier momento**:
- `yunta replay <run> --at <seq>` — estado del run, contexto montado y evidencia disponible en ese instante: responde "¿por qué el agente hizo eso?", hoy imposible en todo el ecosistema (el debugging de flujos de IA es leer transcripts a mano).
- `yunta diff <run-a> <run-b>` — mismo workflow, dos corridas: primer punto de divergencia y qué contexto difería (por hash de segmento).
La caja negra del avión para agentes. Post-v1 temprano: la data ya existe completa; falta la UX de reconstrucción.

## 3. Marketplace con datos: packs publicados con CPTV real
Cuando el registry exista (deuda ⑪), los packs se publican con métricas de corridas reales: mediana de costo por tarea verificada, tasa de re-trabajo, distribución de wall-clock. Elegir workflow deja de ser leer marketing y pasa a ser comparar datos — y crea el efecto red correcto: los packs compiten por eficiencia medible, no por copy. Requisito presente (ya cumplido): stats derivables y exportables del log. Requisito futuro: formato de publicación de métricas agregadas con el pack (diseñar junto al registry; considerar privacidad — solo agregados, jamás contenido de runs).

## 4. Conocimiento compuesto multi-proyecto
El activo que crece con el uso: cada run destila ADRs y contexto (`distill`, §8.3) que los runs siguientes inyectan (`knowledge`). Extensión multi-proyecto **sin mecanismos nuevos**:
- **Capas**: la fuente `knowledge: {}` resuelve `repo > usuario > org` (mismo patrón que config y skills), con precedencia local y parámetro de scope (`knowledge: {layers: [repo]}`) para nodos que no deben contaminarse.
- **La capa org es un knowledge pack** (RFC-0002 íntegro): ADRs transversales y convenciones curadas en un pack versionado (`acme/org-knowledge@vN`), vendoreado con lockfile, congelado por run, actualizado por decisión explícita.
- **Flujo de promoción** (la única pieza nueva, y es un workflow de Yunta): candidatos a promoción desde los `knowledge/` de los repos → gate con `assignee` curador → nueva versión del pack org. El conocimiento pasa de activo por-proyecto a activo de la organización.
- Búsqueda semántica sobre volúmenes grandes: válvula existente vía fuente `mcp` al RAG interno.
Pitch resultante: *el equipo que usa Yunta seis meses tiene un activo que el que empieza hoy no puede comprar — y la org que lo usa en diez repos tiene uno que ningún repo aislado puede construir.* Retención por acumulación de valor, no por lock-in.
