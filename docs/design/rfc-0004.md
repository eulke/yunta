# RFC-0004 — Distribución, licencia y sostenibilidad

**Estado:** aceptado · **Alcance:** titularidad, licencia, canales de distribución, pipeline de release y modelo de sostenibilidad.

## 1. Titularidad y contexto
Yunta es un **proyecto personal** alojado en un repositorio personal, no de la empresa. Se usa dentro del equipo del autor y se publica para cualquiera que quiera usarlo. Consecuencias operativas de esa decisión:
- Separación limpia y demostrable: cuenta personal, equipo propio, tiempo propio; los commits no salen de infraestructura corporativa.
- Antes de publicar: revisar cláusulas de propiedad intelectual y cesión de invenciones del vínculo laboral; si el texto es ambiguo, obtener constancia escrita de no reclamo de titularidad. **Bloqueante de la primera release pública**, no del desarrollo.
- La empresa es un usuario más: consume el binario y publica sus propios packs privados. Nada de configuración, credenciales o conocimiento interno entra al repo público — la arquitectura ya lo garantiza (los packs declaran roles, jamás runners ni secretos; el estado vive fuera del repo).

## 2. Licencia: Apache-2.0
Razones: cláusula expresa de patentes (lo que revisan las áreas legales corporativas antes de aprobar una herramienta), permisividad máxima para adopción, y compatibilidad con el ecosistema Rust, donde es el estándar de facto (frecuentemente en dual MIT/Apache-2.0 — opción válida si se prefiere máxima interoperabilidad). Descartadas: licencias copyleft fuertes (fricción innecesaria para una herramienta de desarrollo que se ejecuta junto a código propietario) y licencias source-available tipo BSL (contradicen el argumento central del producto — un motor de auditoría verificable pierde fuerza si no se puede inspeccionar y correr sin ataduras).
El repositorio incluye `LICENSE`, `NOTICE`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md` y `SECURITY.md` (canal de reporte privado de vulnerabilidades) desde la primera release pública.

## 3. Canales de distribución
Ordenados por prioridad de implementación:
1. **Releases de GitHub con binarios precompilados** — la vía primaria. Linux x86_64/arm64 estático (musl), macOS x86_64/arm64, Windows x86_64. Cada release publica checksums y notas generadas.
2. **Instalador one-liner** (`curl … | sh`) — detecta plataforma, descarga el artefacto correcto, verifica checksum, instala en `~/.local/bin`. Script versionado en el repo, servido desde el dominio o desde raw de GitHub.
3. **`cargo install yunta`** — para quien ya tiene Rust; publica el crate binario junto a `yunta-core`/`yunta-storage`/`yunta-adapters`/`yunta-engine` como dependencias (habilita además embeber el engine).
4. **Homebrew** — tap propio (`<usuario>/tap`), cubre macOS y Linux con esfuerzo mínimo. Migrar a homebrew-core recién con tracción.
5. **GitHub Action oficial** — `setup-yunta`: instala y cachea el binario en CI. Canal de adopción subestimado: mucha gente conocerá Yunta porque aparece en el CI de un repo ajeno.
6. **Imagen de contenedor** — `yunta` + git + toolchain mínima, para pipelines que prefieren imagen a instalación.
7. **winget / scoop** — según demanda real de usuarios Windows.

## 4. Pipeline de release: mecánica
El único gesto humano es empujar un tag `vX.Y.Z`. Regla de orden: **el release de GitHub es el origen de verdad**; ningún canal secundario compila nada — todos consumen sus artefactos. Si un canal secundario falla, el release queda publicado y ese canal se reintenta: un tap desactualizado es un problema aislado, no un release roto.

### 4.1 Jobs
**`test`** (gate de todo lo demás): `cargo test --workspace`, `cargo clippy --workspace -- -D warnings`, `cargo fmt --all --check`, `cargo deny check`, y validación de que los packs de fábrica pasan `yunta check` y corren end-to-end con `mock`. Si falla, no existe release.
**`build`**** (matriz de 5)**, en paralelo:
| Target | Runner | Cómo |
|---|---|---|
| `x86_64-unknown-linux-musl` | ubuntu | `cross build --release` |
| `aarch64-unknown-linux-musl` | ubuntu | `cross build --release` |
| `x86_64-apple-darwin` | macos | `cargo build --release` nativo |
| `aarch64-apple-darwin` | macos | `cargo build --release` nativo |
| `x86_64-pc-windows-msvc` | windows | `cargo build --release` nativo |
musl para Linux porque produce un estático real que corre en cualquier distro sin depender de la glibc del host; macOS y Windows compilan en su propio runner porque cross-compilar hacia ellos cuesta más de lo que ahorra. Cada job empaqueta con **nombre canónico** `yunta-<version>-<target>.tar.gz` (`.zip` en Windows) con el binario, `LICENSE` y `README.md`.
**`release`** (depende de los 5 builds): junta artefactos, calcula SHA-256 en `checksums.txt`, genera notas desde los commits convencionales acumulados desde el tag anterior y crea el release de GitHub.
**Secundarios** (dependen de `release`, paralelos entre sí):
- **`publish-crates`**: publica a [crates.io](http://crates.io) **en orden de dependencia**, esperando disponibilidad en el índice entre pasos — `yunta-core` → `yunta-storage` y `yunta-adapters` → `yunta-engine` → `yunta`. [crates.io](http://crates.io) rechaza un crate cuyas dependencias aún no existan: el orden y la espera no son opcionales. Exige versión compartida en el workspace y dependencias internas por versión exacta.
- **`update-tap`**: renderiza la fórmula de Homebrew desde plantilla (versión, URLs y SHA de los artefactos de macOS y Linux ya resueltos) y commitea al repo del tap con token dedicado. La fórmula solo descarga el binario; no compila en la máquina del usuario.
- **`publish-container`**: build multiplataforma (amd64/arm64) desde imagen base mínima **copiando el binario ya compilado** (no recompila), con git y toolchain mínima. Publica a GHCR con tags `latest`, `X.Y.Z` y `X.Y`.

### 4.2 Instalador (`install.sh`)
Script POSIX único, versionado en el repo, servido por raw de GitHub o dominio propio. Secuencia exacta:
1. Detecta plataforma con `uname -s`/`uname -m` y la mapea al target (`Darwin/arm64` → `aarch64-apple-darwin`, `Linux/x86_64` → `x86_64-unknown-linux-musl`, …). Plataforma no soportada → error con la lista de soportadas.
2. Resuelve versión: `latest` por la API de releases, o `YUNTA_VERSION` para instalaciones pineadas.
3. Descarga el artefacto y `checksums.txt`.
4. **Verifica SHA-256 antes de extraer**; si no coincide, aborta sin escribir nada.
5. Extrae a `~/.local/bin` (o `YUNTA_INSTALL_DIR`): sin sudo, sin tocar directorios del sistema.
6. Si ese directorio no está en `PATH`, imprime la línea exacta a agregar al perfil del shell.
7. Cierra con `yunta --version` y sugiriendo `yunta doctor`.
Requisitos: idempotente (reinstalar reemplaza sin residuos), sin más dependencias que `curl`/`tar`/`shasum`, y `set -eu` — cualquier paso que falle detiene la instalación en vez de dejar el sistema a medias.

### 4.3 GitHub Action (`setup-yunta`)
Repo propio con `action.yml` de composición (pasos de shell; sin JavaScript ni contenedor). Recibe input `version` (default `latest`); consulta la caché de Actions con clave `yunta-<version>-<runner-os>-<arch>`; con hit restaura, sin hit descarga del release, verifica checksum y cachea; agrega el directorio al `PATH` vía `$GITHUB_PATH`. Versionado con **tags móviles** (`v1` → último `v1.x`), que es lo que la gente referencia en sus workflows. Incluye workflow de ejemplo que instala y corre `yunta check`.

### 4.4 Versionado y calidad de release
Semver del binario. El schema de workflows versiona aparte (`yunta_schema`, soporte N y N-1): actualizar Yunta no invalida los workflows del equipo, y esa garantía se publica. Los runs en curso jamás se ven afectados por una actualización — su manifest está congelado (I3). No negociable por release: instalación verificada en contenedor limpio por plataforma, `yunta doctor` como primer comando sugerido, y packs de fábrica verdes en el job `test`.

## 5. Presencia pública
README que enseña a escribir un workflow de tres nodos antes de mencionar packs (D57), sitio de documentación estático generado del mismo contenido, y los packs de fábrica en repos separados del engine — la separación física refuerza que el producto es el motor. Todo en inglés (D46).

## 6. Sostenibilidad
El engine es y seguirá siendo gratuito y abierto: su ubicuidad es lo que da valor a todo lo demás. La monetización, cuando llegue, vive en **un proyecto separado** — el servidor de equipo (estado compartido, gates remotos, dashboard en tiempo real, métricas de organización y, más adelante, ejecución gestionada) — con su propio repositorio y ciclo de vida (D77). Yunta no tendrá capacidades detrás de licencia ni funciones degradadas: la separación de proyectos es lo que hace innecesario ese compromiso.
